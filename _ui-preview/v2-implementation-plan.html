1Principios de "no romper la app"

El objetivo es cambiar solo el aspecto visual — nada de lógica de negocio, nada de cambios en contratos de datos. Para garantizarlo seguimos estos principios:

Regla #1 · La lógica es intocable

No se modifica: server actions (/lib/actions/*), queries (/lib/store/*), adapters (/lib/adapters/*), schema de DB (/drizzle, /src/db), rutas API, middleware de auth (Clerk), Stripe integration, webhooks ni proxies.

Se modifican únicamente: archivos dentro de src/app/[locale]/(dashboard)/**/_components/*.tsx (los Client Components), src/app/globals.css, y se añaden componentes nuevos en src/components/ui/*.

Regla #2 · Backward-compatible CSS

Las clases existentes (.btn-primary, .card, .badge-*, .tab-pill, etc.) siguen funcionando. Solo se cambian sus valores de tokens. Esto permite que archivos que aún no hemos tocado sigan renderizando sin errores.

Ejemplo: --wp-accent cambia de #F97316 a #0F172A. La clase .btn-primary automáticamente se pinta con el nuevo color sin tocar JSX.

Regla #3 · Una vista a la vez, detrás de branch

Cada fase vive en su propia branch (ui/v2-estimates, ui/v2-dashboard, etc.) y se valida en dev antes de merge. Usamos pnpm dev para verificar cada vista funciona — clicks, submits, server actions — antes de pasar a la siguiente.

Regla #4 · Tests visuales + funcionales por vista

Checklist por cada refactor:

  • Render sin errores en build (pnpm build).
  • Interacciones clave siguen funcionando (crear, editar, eliminar, enviar email).
  • i18n español/inglés renderiza correctamente.
  • Mobile viewport (375px) se ve bien.
  • Loading + empty states intactos.
⚠
Lo que NUNCA tocamos sin hablarlo antes: schema de DB, migraciones, Stripe products/prices, Clerk configuration, webhooks, cron jobs, variables de entorno, archivos de proxy o deploy (vercel.json, next.config.ts).

2Arquitectura del rediseño · 3 capas

El rediseño se organiza en 3 capas con dependencia unidireccional (capa N usa capa N-1, no al revés):

Capa 1 · Design tokens (globals.css)

La fuente de verdad. CSS custom properties que definen paleta, spacing, radius, elevation, typography. Si se cambia un token, toda la app se actualiza.

/* Se extiende globals.css con nuevos tokens v2 */
--wp-brand: #0F172A;       /* antes --wp-primary + --wp-accent */
--wp-surface: #FFFFFF;
--wp-surface-2: #F7F7F8;
--wp-text: #18181B;
--wp-text-2: #52525B;
--wp-text-3: #A1A1AA;
--wp-success: #15803D;   /* 700-level, menos saturado */
--wp-elevation-1: 0 1px 2px rgb(0 0 0 / 0.04);
/* Tokens viejos se mantienen como aliases para no romper */
--wp-primary: var(--wp-brand);
--wp-accent: var(--wp-brand);

Capa 2 · Componentes reutilizables (src/components/ui/)

Piezas visuales que aparecen en múltiples vistas. Cada uno toma props tipados y se usa como bloque de construcción.

src/components/ui/ ← carpeta nueva
├── StatusPill.tsx pill con dot + color (sent/approved/paid/…)
├── KpiCard.tsx métrica con label + valor + sub
├── Toggle.tsx switch reutilizable (reemplaza los 5+ inline)
├── ClientAvatar.tsx avatar con inicial · color determinista
├── Segmented.tsx segmented control (tabs tipo iOS)
├── DocHero.tsx hero para estimate/invoice/job detail
├── DetailSidebar.tsx wrapper de cards laterales sticky
├── TimelineList.tsx lista de eventos con dots
├── TotalsCard.tsx card oscura con total + breakdown
├── EmptyState.tsx estado vacío con icon + CTA
└── Toolbar.tsx search + segmented + actions

Capa 3 · Páginas (refactor de los .tsx existentes)

Los *Client.tsx actuales se re-escriben para usar los componentes de capa 2 en lugar de HTML inline. Importante: mantienen sus props y su estado — solo cambia el render.

ⓘ
Beneficio clave: la primera fase (design system) ya hace que el 60% de la app se vea v2 sin tocar ninguna página. Las fases siguientes pulen lo que queda y añaden los componentes nuevos donde tengan más impacto.

1Fase 1 · Design system base

Fase 1 · 0.5 día

Extender globals.css con tokens v2 + crear componentes base

Branch: ui/v2-tokens Risk: Bajo Impacto: 100% de la app cambia de paleta

Paso a paso

  1. Duplicar globals.css en una sección "Legacy tokens" al final del archivo para que las clases antiguas (.btn-primary, .card, .badge-*) sigan teniendo los valores originales como fallback.
  2. Añadir bloque @layer base con los nuevos tokens v2 (--wp-brand, --wp-surface, etc.) y hacer que los tokens viejos sean aliases de los nuevos (ej: --wp-accent: var(--wp-brand)).
  3. Crear src/components/ui/ con los 10 componentes de la capa 2. Cada uno es un .tsx pequeño (50–80 líneas) con TypeScript tipos.
  4. Probar: pnpm dev y navegar Dashboard → Estimates → Invoices. Todo debe verse nuevo sin haber tocado ninguna página. Si un color se ve feo, es porque el token viejo no apuntaba al nuevo — se arregla ajustando el alias.
  5. Merge tras validar que no hay regresiones visuales graves.

Archivos tocados

src/
├── app/
│ └── globals.css → extender con tokens v2 + legacy aliases
├── components/
│ └── ui/ ← carpeta nueva con 10 componentes

Resultado esperado al final de Fase 1

  • Toda la app se ve en paleta navy/neutra (sin orange encendido).
  • Los .btn-primary existentes ahora son navy.
  • Los badges bajan a saturación 700.
  • Existen componentes StatusPill, KpiCard, Toggle, etc. listos para usar.
  • Cero cambios en comportamiento. Tests pasan (si los hay).

2Fase 2 · Estimates (piloto)

Fase 2 · 1.5 días

Refactor de las 4 vistas de Estimates

Branch: ui/v2-estimates Dep: Fase 1 Por qué piloto: vistas completas (list + detail + form + print) → valida todo el sistema

Archivos refactorizados

src/app/[locale]/(dashboard)/estimates/
├── _components/
│ ├── EstimatesClient.tsx → aplicar KPI row, Toolbar, StatusPill, ClientAvatar
│ ├── EstimateDetailClient.tsx → DocHero + DetailSidebar + TotalsCard + TimelineList
│ └── EstimateFormClient.tsx → activar stepper desktop, Toggle reutilizable
└── [id]/print/
└── page.tsx → parties block, CTA navy, logo box

Puntos críticos

  • EstimateFormClient usa useState para mobileStep — conservamos el estado pero lo mostramos también en desktop. La lógica de handleSubmit no cambia.
  • EstimateDetailClient conserva los handlers (handleConvert, handleDelete, handleSendEmail, handleSendSms, handleCopyLink) tal cual. Solo cambia el JSX.
  • EstimatesClient conserva la función deleteEstimate, generateEstimateShareToken, el grouped by month y el filtrado. Lo que cambia es la presentación.
  • Print page es server component — se pasa data a componentes nuevos pero el SSR sigue igual.

Pause & checkpoint antes de seguir

  • Crear un estimate nuevo → se guarda en DB.
  • Editar un estimate → los cambios persisten.
  • Enviar email al cliente → llega.
  • Convert to invoice → genera la invoice correctamente.
  • Portal link abre en /portal/[token].
  • Print preview se ve bien e imprime.
  • Mobile 375px no se rompe.
  • Español/English ambos OK.

3Fase 3 · Core views

Fase 3 · 3 días

Dashboard + Invoices + Clients + Jobs

Branch: ui/v2-core-views Orden sugerido: Invoices → Clients → Jobs → Dashboard Por qué ese orden: Invoices y Clients son muy similares a Estimates (reuso)

Invoices · /invoices · /[id] · /[id]/print · /new

Casi idéntico a Estimates en estructura. Se copia el patrón y se adapta para el concepto de "status de pago" (Draft, Sent, Partial, Paid, Overdue). Agregado nuevo: payment progress bar y timeline de pagos recibidos en el sidebar.

Clients · /clients · /clients/[id] · /new

Lista con agrupamiento alfabético (ya existe en el CSS como .alpha-section — se refactoriza visualmente). Detail incluye hero con LTV, historial de documentos y notas. Riesgo: verificar que el importador CSV sigue funcionando (no se toca su lógica).

Jobs · /jobs · /[id] · /[id]/edit · /new

Aquí hay la mayor decisión de UX: agregamos la vista Kanban como default, con fallback a List. Requiere:

  • Añadir un state viewMode: 'kanban' | 'list' | 'calendar' en JobsClient.
  • La vista Kanban no requiere drag-and-drop en esta iteración (solo visualización). Se usa @dnd-kit que ya está instalado si lo queremos después.
  • El detail mantiene todo lo existente (checklist, fotos, timer) pero con layout 2 columnas + sidebar.

Dashboard · /dashboard

El refactor más grande de la fase. El actual DashboardStats.tsx (252 líneas) se reescribe pero conserva el contrato de Props. El recharts ya está integrado — solo se re-estiliza. Agregado nuevo: card de AI Insights (dummy hasta Fase 5). De momento: se lee de un array hardcodeado.

ⓘ
Flag de feature: para mitigar riesgo, se puede añadir un env var NEXT_PUBLIC_UI_V2=1 que alterne entre la vista vieja y la nueva. Si algo falla en producción, se rollbackea cambiando el flag sin re-deploy. Opcional, pero recomendable.

4Fase 4 · Operations

Fase 4 · 2.5 días

Schedule + Field + Shopping + Team + Expenses + Payments + Referrals

Branch: ui/v2-operations Archivos: 7 (*Client.tsx por vista) Nota: más cosmético que estructural

Vistas sencillas (solo paleta + layout)

Payments, Expenses, Team, Referrals — son listas o grids existentes. Se aplica la paleta v2, toolbar unificada y quick actions. Estimated: 30–60 min cada una.

Vistas con cambio estructural

  • Schedule — actualmente es una lista simple. Se convierte en calendar view de verdad. Opciones:
    • Opción A (rápida): usar un componente de calendario open-source ligero (ej: react-big-calendar o @fullcalendar/react). Pro: rápido de integrar. Con: 1 dependencia extra.
    • Opción B (controlada): construir el grid con flexbox/grid como en el mockup. Pro: control total, sin deps. Con: +1 día de trabajo.
    Recomendación: Opción A si la funcionalidad base es suficiente; Opción B si queremos algo muy custom.
  • Field mode — vista mobile dedicada. Se crea un layout.tsx específico que oculta la nav del dashboard y muestra UI full-screen. La lógica de clock in/out, checklist y fotos ya existe.
  • Shopping list — ya tiene estructura. Se añade agrupamiento por proveedor (requiere un campo nuevo opcional vendor — atención: esto toca DB, se valida antes).
⚠
Decisión pendiente: Shopping list por proveedor requiere añadir columna vendor a la tabla shopping_list_items. Alternativa sin tocar DB: agrupar por el type existente (material / tool / part), o dejar plano por ahora y añadir el feature después.

5Fase 5 · AI surfaces

Fase 5 · 1.5 días

Assistant + AI preferences + Dashboard insights (real)

Branch: ui/v2-ai Archivos: AssistantPageClient.tsx + nuevo AiInsightsCard.tsx + tweaks a AI preferences

Assistant

  • Rediseño del empty state con los 6 casos de uso + atajos /est, /pulse, etc. Los atajos se implementan como onChange del input — si el usuario teclea /, muestra un popover con las opciones (tipo Linear/Raycast).
  • RichBlocks existentes (ChatRenderers.tsx, RichBlocks.tsx) se re-estilizan con la paleta v2.
  • Voice mode — UI existente de VoiceAssistant se re-estiliza para el look hero navy con avatar animado.
  • Model selector se mueve al header como pill compacto (ya casi está así).

Dashboard insights (real, no dummy)

En Fase 3 dejamos los insights como array hardcoded. Aquí los conectamos a AI real. Crear un endpoint /api/ai/insights que llame a Anthropic con context del usuario (últimas facturas, estimates, jobs) y devuelva 3 insights estructurados. Es trabajo nuevo de backend — separarlo en PR propio.

✓
Ya existe la infraestructura: useAssistantChat, parseActions, extractChecklist, ActionButtons, RichChecklist. Solo hay que empaquetar los nuevos prompts para insights y reutilizar los componentes. No reinventamos nada.

!Riesgos y mitigaciones

  • Regresión visual no detectada — Mitigación: screenshot testing manual por vista al final de cada fase. Opcional: añadir Playwright + toHaveScreenshot().
  • Componente nuevo rompe cache de Next — Mitigación: rm -rf .next entre fases si hay comportamiento raro. Añadir force-dynamic si un componente cacheable deja de actualizar.
  • CSS in Tailwind v4 no acepta las nuevas clases — Mitigación: los tokens se definen en @layer base y las clases helper en @layer components. Tailwind v4 soporta esto out of the box.
  • El stepper en desktop confunde a usuarios acostumbrados al form largo — Mitigación: añadir un botón "Ver todo en una página" (fallback) para esta primera iteración.
  • Kanban de Jobs es muy diferente del lista actual — Mitigación: el toggle Kanban | List | Calendar permite a usuarios elegir. Default Kanban pero se recuerda la preferencia en localStorage.
  • Schedule calendar view necesita un range picker, navegación de semanas, sync con time zones — si usamos un lib externo, validar con jobs reales.
  • AI insights dashboard puede ser lento — Mitigación: hacerlo con Suspense y un skeleton. Se carga en streaming, no bloquea el resto del dashboard.
  • Touch targets mobile deben seguir ≥44px para accesibilidad — ya está en los tokens (--wp-touch-min), solo hay que respetarlo.
